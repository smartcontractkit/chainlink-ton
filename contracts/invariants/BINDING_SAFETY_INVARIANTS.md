# Binding Safety Invariants - TON

TON CCIP has three relevant ABI surfaces:
- Tolk contracts under `contracts/contracts/ccip`
- handwritten Go bindings under `pkg/ccip/bindings` and codecs under
  `pkg/ccip/codec`
- generated TypeScript wrappers under `contracts/wrappers/gen/ccip`

The generated TypeScript wrappers are produced from Tolk 1.4.1 and should not be
manually edited. The handwritten Go bindings are the highest binding-drift risk
area because TON does not currently have autogenerated Go bindings.

This file defines expected invariant categories only. This ticket does not add
or require tests.

## Invariant Categories

### TON-BIND-1 - Opcode Consistency

Every opcode used by a Tolk message struct must match the corresponding opcode
used by Go bindings and TypeScript wrappers.

For CRC32-derived Tolk opcodes, `scripts/oplint` can check that the opcode
matches the CRC32 checksum of the struct name. `oplint` is a standalone opcode
checker only; it does not validate Go bindings, TypeScript wrappers, or
cross-language ABI compatibility.

Intentional non-CRC opcodes must be documented next to the Tolk struct with a
`nolint:opcode` comment and a reason, such as compatibility with an existing
CCIP cross-chain selector or external format.

### TON-BIND-2 - Field Ordering Is Identical Across Languages

For each message, storage struct, event, report, and getter result, fields must
be encoded in the same order in Tolk, Go, and generated TypeScript wrappers.

Field names alone are not sufficient. TON cell/TLB encoding is positional, so a
renamed field may still be compatible while a reordered field is not.

### TON-BIND-3 - Inline Cells, References, And Maybe Values Match

Bindings must agree on whether a field is stored inline, stored as a referenced
cell, stored as `Maybe`, or represented by an empty/null value.

High-risk cases include:
- `Cell<T>` and `cell` fields
- `Maybe` / optional fields
- nil slice vs empty slice behavior in Go
- `RemainingBitsAndRefs`
- dictionaries
- snaked cells and linked-list encodings
- event bodies and external log messages

### TON-BIND-4 - Integer Width And Signedness Are Preserved

Bindings must use integer widths and signedness that match the Tolk type and the
CCIP semantic type.

Review must pay special attention to:
- `uint32`, `uint64`, `uint112`, `uint224`, and `uint256`
- `coins` values
- Go `uint64` vs `*big.Int`
- TypeScript `number` vs `bigint`
- downcasts from CCIP common `BigInt` values
- packed values such as split gas prices

Values that cannot fit in the destination type must be rejected before encoding
or before contract-side use.

### TON-BIND-5 - Canonical Cell And BOC Encoding Is Stable

For any value that is signed, hashed, committed, or compared across components,
the encoding must be canonical and stable across Tolk, Go, and generated
TypeScript wrappers.

This includes message hashes, commit reports, execute reports, event payloads,
cross-chain addresses, token amounts, proofs, extra args, and getter-decoded
configuration.

### TON-BIND-6 - Address Encodings Are Explicit

TON-native addresses, cross-chain addresses, and external chain addresses must
not be treated as interchangeable byte strings.

Bindings must preserve:
- TON `address` encoding and `addr_none` behavior
- CCIP cross-chain address length prefixes
- fixed-width byte arrays such as message IDs, roots, and proofs
- rejection of empty, malformed, or all-zero addresses where the contract logic
  requires a real address

### TON-BIND-7 - Getter Decoding Matches Contract Stack Shape

Go readers and TypeScript wrappers must decode getter results with the same
stack width, tuple shape, dictionary encoding, and optional-value conventions
that the Tolk getter returns.

Getter compatibility must be reviewed whenever storage, getter return types, or
generated wrapper output changes.

### TON-BIND-8 - ABI Drift Is Treated As A Security Risk

Any change to a Tolk message, event, storage struct, getter result, or report
format must be reflected in all relevant bindings and codecs before it is
considered complete.
