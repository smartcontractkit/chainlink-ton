# Building Contracts

We use Acton to compile our Tolk contracts. Each contract is declared in `contracts/Acton.toml`, and `yarn build` writes its compiled artifact to `contracts/build/`.

```bash
# Enter the specific #contracts dev shell
nix develop .#contracts

# Build the contracts module
pushd contracts
yarn
yarn build
```

## Nix build

You can also build a `contracts` Nix package:

```bash
nix build .#contracts --print-out-paths # labeled pkg
```

Build `contracts` Nix package without checking out the source code locally:

```bash
nix build 'git+ssh://git@github.com/smartcontractkit/chainlink-ton'#contracts --print-out-paths # labeled pkg
```

## Build system layout

`yarn build` runs `acton build`, which compiles every contract declared in `Acton.toml` (its `display-name`, `src`, and `domain`) and is also the input to abigen tooling. `scripts/actonBuildAdapter.ts` then converts each Acton artifact into `build/<name>.compiled.json`, the shape read by the Jest tests, `yarn generate-pkg` and the Go code.

The legacy Tact examples under `contracts/test/examples/async-communication` are not part of `Acton.toml`. Their compiled code is versioned in `contracts/testdata/legacy-tact` and refreshed with `yarn update:legacy-tact-fixtures`, which builds them through Blueprint from their `wrappers/*.compile.ts` files.

Contract metadata still lives in several places that must be kept in sync by hand.

### Naming contract

Three names must agree for a contract to be consumable end-to-end:

1. **Artifact name** — the name of `build/<name>.compiled.json`. It is the `Acton.toml` contract key, e.g. `LockReleaseLockboxTokenPool` → `build/LockReleaseLockboxTokenPool.compiled.json`. Contracts already released under another artifact name are also written under that legacy name, listed in `contracts/scripts/acton/legacyArtifactNames.json`, e.g. `MCMS` → both `build/MCMS.compiled.json` and `build/mcms.MCMS.compiled.json`, because release packages and the Go deployment code load them by the legacy name. The legacy names stay until those consumers move to the key name. The CCT `JettonMinter`/`JettonWallet` are written only as `ccip.cct.*`, since `scripts/pinArtifacts.ts` writes the reference jetton contracts to `build/JettonMinter.compiled.json` and `build/JettonWallet.compiled.json` (see `scripts/acton/pinnedArtifacts.ts`). Contract keys with a `domain` must be plain identifiers, since `acton wrapper` derives the TypeScript type name from the key. Tests and scripts load code via `contractCode.ccip.local('<name>')`, which reads `build/<name>.compiled.json`.
2. **Package metadata FQN** — the key in `build/contracts-pkg.json`, generated by `contracts/scripts/generateContractsPkg.ts` from its hardcoded `CONTRACTS` list. The Go deployment code (`pkg/bindings`, `deployment/utils/compiled_contracts.go`) looks contracts up by this fully-qualified name, e.g. `link.chain.ton.ccip.pool.LockReleaseLockboxTokenPool`.
3. **On-chain type-and-version name** — the `CONTRACT_NAME` / `FACILITY_NAME` constant in the contract's `types.tolk`, returned by the `typeAndVersion` getter.

`Acton.toml`'s `display-name` should match the on-chain name (convention 3). When adding or renaming a contract, update **all** of: `Acton.toml`, `legacyArtifactNames.json` if the artifact keeps a legacy name, the `CONTRACTS` list in `generateContractsPkg.ts`, the Go constants in `pkg/bindings/index.go`, and the Tolk `CONTRACT_NAME`/`FACILITY_NAME`.
